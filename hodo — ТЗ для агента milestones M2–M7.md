# hodo — ТЗ для агента: milestones M2–M7

Версія від 21.11.2026 · база: 17 крейтів, 135+ тестів, конвеєр \~5 мс/кадр (1200×800, CPU)

## 0. Як користуватися

- Один milestone (або під-пункт M2.1/M2.2…) = одне завдання для одного агента в межах своїх крейтів. Не чіпати чужі зони, поки там працює інший агент.
- Формат кожного блоку: Мета → Скоуп → Безпека → RAM/perf → Тести → Definition of Done.
- Перед стартом: `cargo test --workspace`, зняти baseline `hodo-perf` і записати в опис коміту. Після: ті самі заміри + дельта.
- Усі числа (ліміти, пороги) — стартова пропозиція; агент калібрує за baseline і виносить фінальне значення в `hodo-types`.
- Версії та API сторонніх крейтів (boa, softbuffer, wgpu, html5ever) звіряти з їхньою документацією, а не з пам’яті.

## 1. Глобальні інваріанти

**Код**

- `unsafe_code = forbid` на весь workspace — без винятків. Якщо задача вимагає FFI/sandbox, брати безпечні обгортки з крейтів або виносити рішення мені (див. M3).
- Нова залежність = обґрунтування в коміті, пінована версія, `cargo deny`/`cargo audit` у CI, без `build.rs`, що ходить у мережу.
- Без `Rc/RefCell` у DOM-шарі; хендли — `u32`; застарілі хендли не повинні вказувати на чужий вузол (generation-перевірка при повторному використанні слотів арени).
- Жодних `unwrap/expect/panic!` і необережної індексації на даних з мережі, диска, розширень. Lints вмикати поступово по крейтах, щоб `clippy -D warnings` лишався зеленим.
- Windows — повноцінна ціль: регістр шляхів, CRLF, MAX\_PATH, блокування файлів антивірусом.
- Conventional commits по зонах (`feat(layout): …`, `fix(net): …`), маленькі коміти, без force-push на main.

**Ресурсні ліміти** (одна таблиця констант у `hodo-types`)

- 2 MiB на ресурс/маніфест/локаль (існує).
- Глибина вкладеності DOM/layout/JSON (напр. 512). Переповнення стеку в Rust — це abort, а не паніка, тому ліміт обов’язковий; рекурсію в layout/style робити або ітеративною, або під лімітом.
- Кількість вузлів у документі, довжина атрибутів, кількість CSS-правил, кількість таймерів/портів/повідомлень у черзі, розмір повідомлення між контекстами.
- Для JS: бюджет інструкцій/ітерацій і розмір вхідних значень API.

**Тести (піраміда)**

- unit → піксельні e2e у `hodo-tests` → fuzz у `hodo-fuzz` (корпус поповнювати під кожну нову поверхню атаки) → differential (де є швидкий і повільний шлях) → perf-регресії у `hodo-perf` з порогами в CI.
- Кожен новий парсер/API, доступний ззовні: мінімум один fuzz-таргет і один negative-тест (deny/невалідний вхід).

**RAM/perf**

- Кожен milestone звітує: RSS на холодному старті, RSS з 5 табами, мс/етап (parse/style/layout/render), мс/кадр. Регрес >10% без обґрунтування = блокер.

**Threat model (коротко)**

Три недовірені джерела: веб-контент, розширення, мережа/диск (включно з кешем). Ніхто з них не отримує файлову систему, процеси чи довільну мережу повз permission gate.

## M2. Async/Promises · popup UI · MSG i18n

Зони: hodo-js, hodo-ext-api, hodo-ext-host, hodo-shell. Три підзадачі — три незалежні агенти.

### M2.1 Async/Promises у JS-мосту

**Мета:** bg.js працює зі справжніми API у двох стилях — `browser.*` (Promise) і `chrome.*` (callback) — над тією самою dispatch-таблицею.

**Скоуп**

- Job queue/microtasks у boa: власний виконавець job’ів, drain після кожного task’а. Інтерфейс job queue у boa змінювався між версіями — звірити з 0.22.
- Event loop на контекст розширення: черга task’ів (події API, таймери, повідомлення) → виконати → drain microtasks. Порядок «microtask перед наступним timer» — як у браузерах.
- `setTimeout/setInterval/clearTimeout/clearInterval`: мінімальний крок, ліміт активних таймерів, очищення всіх при знищенні контексту.
- Подвійний стиль виклику: остання аргумент-функція → callback + `runtime.lastError`; інакше → Promise. MV2 `chrome.*` лише callback, `browser.*` завжди Promise, MV3 `chrome.*` підтримує обидва. Реалізація одна, обгортка тонка.
- `runtime.onMessage`: відповідь через `sendResponse`, через `return true` (асинхронно) і через повернений Promise; таймаут очікування; перша відповідь виграє.
- `runtime.connect/onConnect` (Port, `onDisconnect`) — потрібно для popup (M2.2).
- `async/await` у bg.js; відхилені Promise без обробника → лог з іменем розширення, без падіння хоста.
- `fetch` (мінімум: GET/POST, `text()/json()/arrayBuffer()`) лише через `hodo-net`, під `host_permissions`, ліміт 2 MiB, без cookies/credentials за замовчуванням.
- `storage.local` з квотою (\~10 MiB, звірити), `storage.session` (лише RAM, зникає разом із сесією), `storage.onChanged` з `oldValue/newValue`.
- `alarms` (create/clear/onAlarm) на інжектованому годиннику (trait Clock) — тести без реального сну.
- Життєвий цикл: MV2 persistent/event page vs MV3 service worker. Для MV3 — вивантаження контексту після простою; подія будить його знову; стан живе в `storage`, а не в JS-глобалах. Фоновий контекст в idle не тримає RAM.

**Безпека**

- Глобали інжектяться лише для дозволених namespace (вже в плані); API-об’єкти заморожені; з JS немає шляху до внутрішніх хендлів хоста.
- Boa не має вбудованого переривання за wall-clock: використати runtime limits (loop iteration, recursion, stack) як проксі; справжній kill — після M3.
- Повідомлення між контекстами: тільки JSON-подібні типи, ліміти розміру/глибини, цикли відхиляти.
- CSP: MV3 — заборона `eval`/`new Function`/віддаленого коду; MV2 — дефолт `script-src 'self'; object-src 'self'`. Манифестний `content_security_policy` валідувати й ніколи не послаблювати нижче дефолту.
- Окремий origin на розширення: випадковий id на встановлення (не стабільний — проти fingerprinting), схема `hodo-ext://<id>/`, назовні видно лише `web_accessible_resources`.

**Тести:** еталонні послідовності порядку microtask/timer; 8 існуючих демо без регресу; нові демо `async-chrome` і `promises-gecko`; fuzz на вхід `sendMessage`/`storage.set` (великі, вкладені, циклічні значення); deny-тест на кожен новий namespace.

**DoD:** обидва стилі API проходять спільний набір тестів; unhandled rejection не валить хост; idle-контекст MV3 вивантажується; fuzz без паніки; clippy/fmt/тести на двох ОС.

### M2.2 Popup UI розширень

**Мета:** клік по іконці розширення відкриває popup з HTML/CSS/JS пакета, відрендерений рушієм hodo.

**Скоуп**

- Toolbar action: `action` (MV3) / `browser_action` (MV2): іконка (PNG, вибір розміру за DPI), `title`, `setBadgeText/BackgroundColor`, `setPopup`, `onClicked` (якщо popup не заданий), `enable/disable`. Малювати в `hodo-shell`; багато іконок → overflow-меню.
- Popup — окрема поверхня з власним конвеєром html → layout → render. Розмір за вмістом з обмеженням (орієнтир Chrome: від 25×25 до 800×600, звірити), скрол усередині при переповненні. Закривається по Esc/втраті фокуса/кліку поза: контекст і піксельний буфер знищуються.
- Скрипти в popup потребують мінімальних DOM-біндингів у `hodo-js`: `getElementById`, `querySelector(All)` (спершу прості селектори), `textContent`, `value`, `classList`, `setAttribute`, `createElement/appendChild/removeChild`, `addEventListener` (click, input, keydown, DOMContentLoaded), `window.close()`. `innerHTML` — відкласти або тільки через той самий html5ever з лімітами.
- Мутація DOM → dirty-флаги → перелейаут/перемал. До M5 це повний перерахунок, але інтерфейс dirty-флагів закласти зараз.
- Hit-testing по layout-боксах → click/hover/focus; Tab-навігація; це база для форм у M7.
- Popup ↔ background через `runtime.sendMessage/connect`.
- Базовий user-agent stylesheet для popup (шрифт, margin).

**Безпека**

- CSP popup: без inline `<script>` і inline-обробників (`onclick=`), лише `<script src>` з пакета; зовнішні ресурси — тільки через `host_permissions`.
- Popup не бачить DOM вкладок. `window.open`/навігація всередині popup — через gate або в нову вкладку; `javascript:` і `data:` для top-level навігації заборонені.
- DOM-хендли в JS — непрозорі, з generation-перевіркою.

**RAM:** popup-контекст живе лише поки відкритий; піксельний буфер дорівнює розміру popup.

**Тести:** піксельний знімок popup-chrome; roundtrip click → message → badge; закриття popup звільняє контекст (лічильник живих контекстів); fuzz на DOM-біндинги (випадкові `appendChild/removeChild` по застарілих хендлах).

**DoD:** `popup-chrome` повністю інтерактивний; після закриття витоків контекстів немає; ресурси popup під тими ж лімітами.

### M2.3 MSG i18n

**Скоуп**

- `_locales/<locale>/messages.json`: `message`, `description`, `placeholders` (`$name$` → `content: $1`), `$$` = літерал `$`. Предефіновані: `@@extension_id`, `@@ui_locale`, `@@bidi_dir`, `@@bidi_reversed_dir`, `@@bidi_start_edge`, `@@bidi_end_edge`.
- Заміна `__MSG_name__` у manifest (name, description, `default_title` тощо) і в CSS пакета. У HTML автоматично не заміняти — тільки через `i18n.getMessage`.
- Fallback: точна локаль (нормалізувати `uk-UA`/`uk_UA`) → мова (`uk`) → `default_locale`; відсутній ключ → порожній рядок + warning. `default_locale` обов’язковий, якщо є `_locales`.
- API: `i18n.getMessage(name, substitutions)` (до 9 підстановок, рядок або масив), `getUILanguage`, `getAcceptLanguages`; `detectLanguage` — явний Unimplemented або спрощений.
- Мова UI: з ОС через безпечний крейт-обгортку (без unsafe), override через `--lang` / `about:hodo`.

**Безпека:** повідомлення — завжди плейн-текст, ніколи не HTML. Ліміти: 2 MiB на файл, кількість ключів, довжина значення, ім’я ключа тільки `[A-Za-z0-9_@]`. Підстановка плейсхолдерів — один прохід, без рекурсії (захист від expansion bomb). Битий або відсутній locale не валить розширення — деградація до `default_locale`.

**Тести:** порядок fallback; плейсхолдери та `$$`; bidi-предефайни; `__MSG_` у manifest обох діалектів; битий JSON; 10 000 ключів; `i18n-gecko` без регресу.

### M2 — загальний Definition of Done

- Усі три підзадачі змерджені, workspace-check зелений на ubuntu і windows.
- `hodo-perf`: parse/style/layout/render не гірші за baseline більш ніж на 10%.
- Нові fuzz-таргети (JS-міст, DOM-біндинги, messages.json) додані в `hodo-fuzz`, 0 паніок.

## M3. Ізольовані процеси розширень

**Мета:** кожне розширення (bg-контекст) виконується в окремому ОС-процесі з мінімальними правами; падіння, зависання чи зловмисність одного не зачіпає браузер і інші розширення.

**Рішення до старту (відкрите питання):** ОС-sandbox (Windows: restricted token / AppContainer / Job Object; Linux: seccomp / Landlock) зазвичай потребує FFI, а FFI — це `unsafe`. Варіанти: (A) лишити `unsafe_code = forbid` скрізь і користуватись безпечними обгортками з крейтів (кандидати, актуальність перевірити: `landlock`, `seccompiler`, `rustix` із safe API, `win32job`, `interprocess`); (B) один мінімальний крейт `hodo-sandbox` з документованим винятком і аудитом. Рекомендація: A; B — лише якщо A не дає потрібних гарантій на Windows. Workspace-lint без явного рішення не міняти.

**Скоуп**

- Архітектура: `hodo-ext-host` (broker) у головному процесі + новий бінарник `hodo-ext-worker` (один на розширення): `hodo-js` і мінімальний runtime. Permission gate живе тільки в broker.
- IPC: локальні pipes (stdio або named pipe/UDS), фрейми з префіксом довжини, serde-протокол з версією; ліміти на розмір фрейму (напр. 1 MiB), довжину черги й частоту запитів; без shared memory.
- Worker надсилає запити API (`storage.*`, `fetch`, `tabs.*`…) → broker перевіряє permission → виконує → відповідає. У worker немає ні FS, ні мережі: `fetch` іде через broker і `hodo-net`.
- Життєвий цикл: spawn за запитом/подією, idle-вивантаження (особливо MV3), watchdog (heartbeat + wall-clock на task) → kill процесу при зависанні. Саме це закриває прогалину boa без wall-clock переривання. Рестарт з backoff і лімітом спроб; crash → подія в лог/`about:hodo`, не падіння браузера.
- Ліміти на процес: пам’ять (Windows — Job Object memory limit; Linux — безпечний шлях через rlimit/cgroups), CPU-time, кількість handle, дочірні процеси заборонені.
- Sandbox: Windows — Job Object (kill-on-close, заборона дочірніх процесів), далі restricted token/AppContainer; Linux — Landlock (без FS) + seccomp allowlist + no\_new\_privs; macOS поки не ціль. Worker стартує з очищеним env, порожнім temp як cwd і закритими успадкованими handle.
- Якщо ОС-механізм недоступний: fail-closed + явне попередження в `about:hodo`; режим `--insecure-no-sandbox` лише для розробки.
- Popup-скрипти (M2.2) теж виконуються у worker; рендер лишається в головному процесі.

**Безпека**

- Broker не довіряє нічому з worker: усі повідомлення — недовірений вхід (fuzz протоколу).
- Handshake із секретним токеном сесії; канал прив’язаний до id розширення, worker не може видати себе за інше.
- Anti-confused-deputy: permission gate бере id розширення з каналу, а не з тіла повідомлення.
- Поведінка API для розробника розширень не змінюється відносно M2.

**RAM/perf**

- Процес на розширення додає базову ціну RAM (boa + runtime) — виміряти й задокументувати; ліміт одночасних worker’ів, idle-вивантаження. Режим `--ext-in-process` для low-RAM (менше ізоляції) — лише явним прапором, не default.
- Бенчмарк roundtrip виклику API через IPC (ціль — калібрувати за baseline).

**Тести**

- Kill worker посеред task’а → broker живий, подія в лог, рестарт з backoff.
- Нескінченний цикл або виділення пам’яті в bg.js → процес убитий за лімітом, інші розширення не постраждали.
- Тест-розширення, що пробує відкрити файл/сокет, → заборонено на рівні ОС (окремо на ubuntu і windows).
- Fuzz IPC-протоколу: збиті фрейми, величезні довжини, чужа версія, повторний handshake.
- 8 демо проходять і з ізоляцією, і з `--ext-in-process`.

**DoD:** усі 8 демо працюють у worker; kill/OOM/hang-тести зелені; sandbox увімкнений за замовчуванням на Windows і Linux; threat model оновлено; RSS-дельта описана.

## M4. hodo-cache у hodo-net

**Мета:** повторні завантаження без мережі або з умовними запитами; диск-LRU; мінімальна RAM (метадані в RAM, контент на диску); без нових векторів атаки.

**HTTP-семантика** (за RFC 9111, приватний кеш браузера)

- Ключ = (GET, нормалізований URL без фрагмента, partition key). Partition key = top-frame site (для розширень — id розширення). Без партиціювання кеш-таймінг дає крос-сайтове відстеження.
- Що кешувати: GET зі статусами 200/203/204/301/308/404/410 (206 — відкласти). Не кешувати: `Cache-Control: no-store`, відповіді з `Authorization` без явного дозволу (public/must-revalidate), `Vary: *`.
- Свіжість: `max-age`, `Expires`, `Age`, `Date`; евристика при `Last-Modified` без явного TTL (10% віку з верхнім кепом, напр. 24 год); `no-cache` = зберігати, але завжди ревалідувати; `must-revalidate`; `stale-while-revalidate`/`stale-if-error` — опційно.
- Ревалідація: `ETag` → `If-None-Match`, `Last-Modified` → `If-Modified-Since`; 304 → оновити метадані (merge заголовків), віддати збережене тіло; слабкі ETag коректно.
- `Vary`: зберігати значення релевантних request-заголовків; мінімум — `Accept-Encoding`; невідомі → не кешувати.
- Single-flight: одночасні запити одного ключа → один мережевий запит.
- Режими: `--offline` (лише кеш, помилка при промаху — для тестів), private (без диска), `--no-cache`.
- Інвалідація: `clear_cache()`, `about:hodo` показує hits/misses/bytes/evictions; небезпечний метод (POST/PUT/DELETE) на URL інвалідує запис.

**Диск і формат (hodo-cache)**

- Файл на запис; ім’я = хеш ключа (hex), шардінг по перших 2 символах, каталог — всередині профілю. Шлях будується лише з хеша, тож path traversal неможливий, а короткі імена знімають проблему MAX\_PATH на Windows.
- Формат: версійований заголовок (magic + version + довжини + checksum), далі метадані, далі тіло. Читання перевіряє довжини й checksum; розбіжність → запис викидається, без паніки.
- Запис атомарний: temp-файл у тому ж каталозі → fsync → rename; на Windows retry з backoff при блокуванні антивірусом.
- Індекс у RAM: ключ → (розмір, час доступу, свіжість, шлях); при старті відновлюється скануванням каталогу. Бюджет RAM на індекс обмежений.
- Квота диска (напр. 128–256 MiB, налаштовується), LRU-евікшн. Ліміт запису 2 MiB (існуючий хардкап) застосовується до розпакованого розміру — захист від gzip-бомби: кеш зберігає лише те, що вже пройшло ліміти net.
- Права на каталог — тільки поточний користувач. Без mmap (потребує unsafe): читання в буфер, який звільняється після використання.

**Безпека**

- Cache poisoning: не кешувати відповіді з помилками парсингу заголовків; єдиний модуль нормалізації URL для net і cache; `Content-Length` не довіряти — звіряти з фактично прочитаним.
- `Set-Cookie` не кешувати й не відтворювати з кешу.
- Кілька процесів (після M3): єдиний власник кешу в broker або файловий lock; ніколи не два writer’и одного файлу.

**RAM/perf:** холодне vs тепле завантаження демо-сторінки з ресурсами; RSS не росте разом із кешем на диску (зафіксувати байти метаданих на запис); у `hodo-perf` — сценарій warm-cache.

**Тести**

- Матриця `Cache-Control` × вік × валідатори на інжектованому годиннику (trait Clock).
- 304-флоу, Vary, no-store, Authorization, кеш редіректів (301/308).
- Crash-safety: обрізаний/побитий файл, обрив посеред запису (емуляція), перезапуск з відновленням індексу.
- Евікшн під квотою, LRU-порядок; Windows-специфіка (довгі URL, регістр).
- Fuzz: парсери `Cache-Control`/`Vary`/`ETag`, формат файлу кешу.
- Negative: `..`, `%2e%2e`, зворотні слеші в URL не впливають на файловий шлях.

**DoD:** net використовує cache за замовчуванням (прапор вимкнення є); тести зелені; warm-load швидший за cold без росту RSS; fuzz-таргети додані.

## M5. Incremental layout + частковий repaint

**Мета:** після зміни DOM, стилів чи скролу перераховувати й перемальовувати лише змінене; мінімальний час кадру і \~0% CPU в idle.

**Відправна точка (за поточним baseline):** на 1200×800 render ≈ 5 мс, а parse + style + layout разом ≈ 0.15 мс. Отже, основний виграш — у repaint (damage-rect, scroll-blit), а інкрементальний layout виправданий тільки на великих документах (тисячі вузлів) і при динамічних змінах (JS, popup). Порядок: M5.1 → M5.2 → M5.3; M5.3 стартує лише після бенчмарка на великому документі, який показує, що layout справді вузьке місце.

### M5.1 Display list і damage tracking

- Крок render будує display list: `Vec` команд (FillRect, Border, GlyphRun, Image, Clip…), кожна з bounding rect і прив’язкою до вузла/боксу. tiny-skia малює зі списку.
- Diff старого й нового списку (за id вузла + хеш команди) → damage region. Union прямокутників; якщо rect’ів забагато або площа > \~50% — повний перемал (пороги калібрувати).
- Малювати лише в межах damage (clip), попередній кадр перевикористовувати.
- Презент: softbuffer вміє передавати damage-регіони ОС (перевірити API у використаній версії) — віддавати лише змінені rect’и.
- Каретка/blink — окремий малий damage без перелейауту.
- Idle: `ControlFlow::Wait`, redraw лише по подіях; інвалідації коалесувати в один кадр.

### M5.2 Scroll blit

- Скрол = зсув наявного піксельного буфера (`copy_within` по рядках) + перемал лише відкритої смуги, а не повний кадр. Fixed/sticky елементи (коли з’являться) — окремо.
- Скрол не запускає style/layout, лише paint. Тест: лічильник викликів layout під час скролу = 0.

### M5.3 Incremental style/layout

- Dirty-біти в паралельних масивах за `u32`-хендлами: style-dirty, layout-dirty, paint-dirty, has-dirty-descendant. Це лягає в arena-DOM без `Rc/RefCell`.
- Журнал мутацій DOM: зміна attr (class/id/style) → restyle; text → relayout; insert/remove → relayout батька + restyle сусідів (для `+`/`~` після M7).
- Invalidation: який набір правил зачеплений зміною class/id/attr (індекс правил за ключем). Після M7 (descendant-селектори) invalidation переглянути: зміна предка зачіпає піддерево.
- Layout: boundaries (бокс з фіксованою шириною/overflow, що не залежить від вмісту) зупиняють поширення; кеш результату бокса за (available width, хеш стилю); зміна висоти дитини йде вгору з урахуванням margin collapse.
- Кеші тексту: ширини text-run за (шрифт, розмір, хеш тексту), кеш line-break; glyph-кеш fontdue обмежений за розміром (LRU) — це RAM.
- Принцип «пікселі тільки в активного табу»: неактивний таб скидає піксельний буфер і display list, зберігає DOM + стилі; через час T (калібрувати) скидає й layout-дерево (відновлюється при активації). Узгодити з idle-вивантаженням JS-контекстів (M2/M3).

**Безпека/надійність**

- Інкрементальний шлях — джерело тонких багів: результат має бути піксель-в-піксель рівний повному relayout/repaint.
- Ліміти: розмір display list, кількість dirty-rect, глибина пропагації.
- `debug_assert` на інваріанти + у release fallback на повний перерахунок із лічильником у `about:hodo` (помилка інкременталізму не валить браузер).

**Тести**

- Differential property-тест: випадкові послідовності мутацій (attr/text/insert/remove/scroll) на корпусі `hodo-fuzz` і демо-сторінках → incremental == full, піксельно.
- Прапори `HODO_FORCE_FULL=1` (вимкнути інкременталізм) і `HODO_DEBUG_DAMAGE=1` (малювати damage-рамки).
- Бенчмарки в `hodo-perf` на великому документі (\~10k вузлів): (а) зміна одного тексту, (б) зміна class на корені секції, (в) скрол на рядок і на сторінку. Пороги в CI калібрувати після baseline; ціль — зміна одного вузла ≪ повного кадру.
- Лічильники в `about:hodo`: layout-runs, повні/часткові repaint, % перемальованих пікселів.

**DoD:** differential-набір зелений; скрол без layout; idle ≈ 0% CPU; перемальовується лише damage; RSS не вище baseline (display list і кеші в межах бюджету).

## M6. wgpu за feature-флагом

**Мета:** опціональний GPU-бекенд рендера; CPU (tiny-skia) лишається за замовчуванням і завжди доступним.

**Скоуп**

- Спершу абстракція: display list (M5.1) → trait бекенду (`PaintBackend`: prepare / paint / present, resize, damage). CPU-бекенд — поточний; GPU — новий, за cargo feature `gpu` і runtime-прапором `--gpu` (або налаштуванням в `about:hodo`). Без M5.1 цей milestone не стартує.
- GPU: прямокутники/бордери (instanced quads), glyph-атлас (fontdue растеризує → атлас-текстура з LRU-евікшном), зображення (текстури з PNG/JPEG), clip через scissor. Шейдери — тільки наші, нічого від веб-контенту.
- Surface — безпечним API (winit 0.30 + `Arc<Window>`); async-запит адаптера через `pollster` або подібне; `unsafe` у нашому коді немає.
- Fallback: немає адаптера / помилка / device lost → автоматично CPU-бекенд з повідомленням у логу, без падіння. Обробити resize, DPI, minimize/restore.
- Ліміти: розміри текстур ≤ лімітів адаптера (clamp + тайлінг великих зображень), бюджет VRAM для атласу, ліміт вершин за кадр.
- Залежності: wgpu важка (час збірки, розмір бінарника, RSS драйвера). Feature ізольований так, щоб CPU-збірка його не тягнула взагалі; `cargo deny` на нові транзитивні залежності.

**Суперечність з принципом «мінімум RAM»**

GPU зазвичай збільшує RSS (драйвери, шейдер-кеші). Тому GPU вимкнений за замовчуванням, у perf-звіті — RSS CPU vs GPU, а велика дельта фіксується в README як явний trade-off, а не маскується.

**Безпека**

- GPU — додаткова поверхня атаки (драйвери). У GPU потрапляє лише наша геометрія; валідацію wgpu не вимикати; довільних шейдерів чи форматів текстур із контенту немає.
- Розміри зображень обмежуються до завантаження в GPU (розпаковані байти ≤ ліміт, див. 2 MiB cap + декодер).
- Бекенд приймає тільки display list і не має доступу до JS/розширень.

**Тести**

- CI: збірка і clippy з `--features gpu` на ubuntu і windows (compile-check); GPU-тести з реальним адаптером — `#[ignore]` або через software-адаптер (WARP/lavapipe), якщо доступний.
- Піксельне порівняння CPU vs GPU з допуском (±N на канал — антиаліасинг відрізняється), окремі golden-и на бекенд; бітової ідентичності не вимагати.
- Fallback-тести: примусова відмова адаптера → CPU, без паніки.
- Fuzz: display list з екстремальними значеннями (NaN, величезні rect’и, від’ємні розміри) не валить жоден бекенд.

**DoD:** `cargo build` без feature не змінився (залежності, час, RSS); з feature демо-сторінка рендериться на GPU в межах допуску; fallback працює; perf/RSS-звіт додано.

## M7. Селектори · inline box model · таблиці/форми · flexbox/grid

Розбити на незалежні підзадачі M7.1 → M7.5; кожна має власний набір піксельних e2e і fuzz-корпус. Порядок виконання — як нумерація.

**Рішення до старту:** власний матчер селекторів чи крейт `selectors` (Servo). Перевірити, чи чисто він інтегрується з arena-DOM (потрібен trait `Element` на `u32`-хендлах із контекстом). Якщо так — брати крейт (менше багів, специфічність уже коректна); якщо ні — власний матчер з тестами за таблицею специфічності.

### M7.1 Селектори (hodo-css, hodo-style)

- Комбінатори: descendant (пробіл), child `>`, adjacent `+`, general sibling `~`.
- Прості: type, `*`, `.class`, `#id`, атрибутні `[a]`, `[a=v]`, `~=`, `|=`, `^=`, `$=`, `*=` (з прапором `i`).
- Pseudo-class: `:first-child`, `:last-child`, `:nth-child(an+b)`, `:only-child`, `:not()` (простий аргумент), `:root`, `:empty`. `:hover/:focus/:active` — після M2.2/M7.3 (стан живе в shell). `:is()/:where()` — опційно.
- Специфічність (a,b,c) і порядок джерел точно за спекою; `!important`; порядок user-agent < author < inline style.
- Матчинг справа наліво; індекс правил за ключем найправішого compound (id → class → tag → universal); Bloom-фільтр предків (тег/клас/id) під час обходу дерева, щоб швидко відсікати descendant-селектори; кеш для sibling-залежних правил.

**Безпека/ліміти:** довжина селектора і кількість compound’ів (напр. ≤ 64), кількість правил, глибина `:not/:is`; жодного катастрофічного backtracking — тест на патологічні селектори на глибокому DOM з часовим бюджетом; невалідний селектор відкидає лише своє правило, а не весь файл (error recovery за CSS-спекою).

**Тести:** таблиця специфічності; приклади зі spec; патологічні селектори; fuzz CSS-парсера з новими конструкціями.

### M7.2 Inline box model (hodo-layout)

- Inline formatting context: line boxes, `span/a/em/strong/code`; фрагментація inline-елемента по рядках (бордер і фон на кожен фрагмент); горизонтальні margin/padding впливають, вертикальні — ні; `vertical-align: baseline|top|middle|bottom`; `line-height`; `inline-block`.
- Анонімні блоки: змішаний inline + block вміст у block-контейнері.
- Текст: white-space (`normal`, `nowrap`, `pre`, `pre-wrap`, `pre-line`), `<br>`, `text-align` (justify — опційно), `text-indent`, `letter-spacing/word-spacing`, `text-decoration`, `overflow-wrap/word-break` (довгі слова без пробілів обов’язково, інакше горизонтальний overflow).
- Шрифти: fallback-ланцюг для відсутніх гліфів; `font-weight/style` (синтетичний або окремі файли); ascent/descent з fontdue → baseline-вирівнювання.
- Hit-testing по фрагментах inline-бокса, а не по bounding box цілого елемента — база для кліків по `href`.
- Bidi/комплексні скрипти — поза скоупом (явно задокументувати); кирилиця й латиниця працюють.

**Безпека/ліміти:** кількість line box’ів і довжина тексту; захист від O(n²) при line-break на дуже довгому тексті (пошук точки розриву з кешем ширин); глибина вкладених inline під лімітом (стек).

**Тести:** піксельні e2e (змішаний inline, фрагментація бордера, baseline); довге слово; `white-space: pre`; клік по лінку, що переноситься на два рядки; fuzz на глибокі `span` і величезні тексти.

### M7.3 Таблиці й форми

**Таблиці**

- Генерація табличних боксів (table / row-group / row / cell + анонімні, коли HTML невалідний); `caption`, `thead/tbody/tfoot`, `colspan/rowspan`.
- Етап 1: `table-layout: fixed`. Етап 2: auto-алгоритм (min/max-content ширини колонок, розподіл залишку), `border-collapse` collapse/separate, `border-spacing`, padding клітинок, `vertical-align` у клітинці.
- Ліміти проти DoD-атак на розмір сітки: colspan ≤ 1000, rowspan ≤ 65534 (як у HTML-спеці), загальна кількість клітинок ≤ бюджет (напр. 100k), глибина вкладених таблиць під лімітом.

**Форми**

- Контроли: `input` (text/password/checkbox/radio/button/submit/reset), `textarea`, `select` (+ popup-список), `button`, `label`, `fieldset/legend`; disabled/readonly/placeholder.
- Фокус, caret, редагування тексту (вставка/видалення/стрілки/Home/End; IME — поза скоупом), Tab-порядок, `label` → активація контролу; `:focus/:checked/:disabled`.
- Сабміт: GET (query) і POST `application/x-www-form-urlencoded` (multipart/file — пізніше). Потрібні зміни в `hodo-net`: тіло запиту (ліміт 2 MiB), коректні редіректи 303/307/308.
- Безпека: навігація лише на http/https (жодних `javascript:`/`data:` для top-level); пароль маскується в рендері й не потрапляє в логи, кеш, історію; POST-відповіді не кешуються (M4); `input type=file` — поза скоупом (sandbox); `form action` із розширень — через gate.
- Ліміти: довжина значення поля, кількість контролів, розмір сабміту.

**Тести:** піксельні e2e контролів; клавіатурні сценарії; сабміт GET/POST через локальний тестовий сервер; fuzz на таблиці (величезні colspan/rowspan, вкладені) і форми.

### M7.4 Flexbox

- Алгоритм за CSS Flexbox: `display: flex/inline-flex`, `flex-direction`, `flex-wrap`, `flex-grow/shrink/basis` (+ шорткат `flex`), `justify-content`, `align-items/align-self/align-content`, `gap`, `order`, `min/max-width/height` із циклом clamp, `margin: auto`.
- Спершу single-line, потім multi-line (wrap). Пастка: `min-width: auto` у flex-елементів (content-based minimum).
- Відсоткові розміри й циклічні залежності — поступова деградація без паніки.

**Ліміти/безпека:** кількість flex-елементів; ітерації resolve-flexible-lengths обмежені; жодних NaN/inf (clamp вхідних значень).

**Тести:** власні піксельні еталони (у дусі WPT); патологічні (нульовий flex-basis, надвеликий grow); fuzz числових значень.

### M7.5 Grid

- `display: grid`, `grid-template-columns/rows` (px, %, `fr`, `auto`, `minmax()`, `repeat()`), `gap`, auto-placement (row/column, без dense), явне розміщення `grid-column/row` (лінії, span). Без subgrid, named areas і masonry на першому етапі.
- Track sizing — спрощено, але детерміновано; відхилення від спеки явно задокументувати.

**Ліміти:** кількість треків (напр. ≤ 1000, калібрувати) — `repeat(99999, …)` обрізається; ліміт неявних треків.

**Тести:** піксельні e2e, патологічні `repeat`, fuzz.

### M7 — що ще блокує реальні сайти (поза переліком)

`position` (relative/absolute/fixed/sticky), `float`, `overflow`, `z-index`/stacking, `box-sizing`, `min/max-width`, CSS-змінні `var()`, `calc()`, `@media` (viewport), `@font-face`, background-image/gradient. Рекомендую винести в окремий M8 і розставити пріоритети за реальними сторінками.

**Загальне для M7:** розширити `hodo-fuzz` корпусом: глибокі вкладення (1000+ рівнів), величезні таблиці/grid, патологічні селектори, шалені числа (NaN/inf/1e308), CSS-бомби за кількістю правил. Жоден випадок не дає паніки, abort (stack overflow) чи зависання понад бюджет.

**DoD M7:** кожна підзадача має власний e2e-набір + fuzz; perf-регрес < 10% на базовій демо-сторінці; нові фічі під лімітами; таблиця «підтримувані властивості» (property → статус) оновлена.

## Рекомендований порядок і залежності

Моя пропозиція (не обов’язкова):

1. **M2.1** (promises/event loop) — розблоковує реальні розширення.
2. **M7.1 + M7.2** (селектори, inline) — без них popup і реальні сторінки виглядають зламано; кліки по лінках залежать від inline-фрагментів.
3. **M2.2 + M2.3** (popup UI, i18n) — popup потребує DOM-біндингів і коректного inline.
4. **M3** (ізоляція) — після M2: API-поверхня вже стабільна, а ізоляція страхує все, що додалося.
5. **M4** (кеш) — незалежний, можна паралельно з M3; бажано до M5, бо впливає на perf-бенчмарки.
6. **M5.1/M5.2** (damage + scroll-blit) — відразу видимий виграш; **M5.3** — після бенчмарка на великому документі й після M7.1 (invalidation залежить від descendant-селекторів).
7. **M7.3–M7.5** (таблиці/форми, flex, grid).
8. **M6** (GPU) — останнім: потребує стабільного display list і не є пріоритетом для цілі «мінімум RAM».

Залежності коротко: M5.1 → M6; M2.2 → M7.3 (hit-testing, фокус); M7.2 → кліки по лінках; M3 після M2; M4 і M3 домовитися про власника кешу.

## Відкриті рішення (потрібні від власника проєкту)

1. Sandbox і `unsafe`: варіант A (лише безпечні крейти) чи B (`hodo-sandbox` з винятком).
